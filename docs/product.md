# OctoRill 内部产品参考

这份文档供 specs、实现讨论和协作者同步产品口径时使用。公开概览请看 `docs-site/docs/product.md`；这里保留更完整的行为语义和实现边界。若你是第一次进入仓库，建议先看 [`../README.md`](../README.md)、[`docs/README.md`](./README.md) 与 [`architecture.md`](./architecture.md)。

## 产品定位

OctoRill 面向需要持续查看 GitHub 动态的个人用户。它把“与我直接相关”的信息收束成一个阅读工作区：关注仓库的发布更新、他人对我的社交反馈、按用户时区回顾昨天自然日的日报，以及 GitHub Inbox 入口。

目标不是替代 GitHub，而是减少以下摩擦：

- 为了追发布更新频繁切换仓库页、Release 页和通知页
- 想快速理解 release 内容时只能直接啃原文
- 需要回顾最近一轮变化时，没有一个稳定的个人视角窗口

润色与日报的价值在于替读者理解变化：读取发布说明、PR 或代码差异是生成过程的工作，阅读正文应直接给出有依据的变化与必要说明。领域用语见根目录 [GLOSSARY.md](../GLOSSARY.md)。

## 主要对象与信号

### Release

Release 是主阅读对象，承担最多的衍生能力：

- **全部（聚合）**：按用户时区的本地自然日分组展示 Dashboard 活动流；当前日组直接显示原始活动卡片，历史日组默认优先显示对应日报，并允许在“日报视图”和“日期分界 + 原始活动列表”之间单独切换。历史日报会紧凑概括同一天内的 Release 及实际发生的获星 / 关注；在日报视图下，已被摘要覆盖的社交卡片不再重复出现，切回列表视图后仍可查看同日原始混排活动卡片。
- **发布**：左侧展示按本地自然日分组的 Release 信息流（Feed）；仅在日组切换处显示弱化日期分隔线，首个可见日组不显示前置分隔，右侧展示「Inbox 快捷入口」。
- **加星**：左侧仅展示“谁给我的个人仓库加星”的社交活动卡片，按同一本地自然日分组；右侧展示「Inbox 快捷入口」。
- **关注**：左侧仅展示“谁关注了我”的社交活动卡片，按同一本地自然日分组；右侧展示「Inbox 快捷入口」。
- **日报**：左侧展示日报内容查看（并支持手动生成）；右侧展示「日报列表 + Inbox 快捷入口」。
- **收件箱**：左侧展示通知列表（用于查看与跳转），不进入 Feed；右侧仍展示 Inbox 快捷入口。

### 社交动态

当前只覆盖两类“与我直接相关”的社交反馈：

- `repo_star_received`
- `follower_received`

这两类卡片保持轻量，只展示必要身份信息、时间和 GitHub 跳转入口，不引入 AI lane。

公告（GitHub Discussions Announcements）属于 `全部` tab 中的内容卡阅读项，而不是轻量社交流；它与 Release 一样支持 `原文 / 翻译 / 润色`，标题进入站内 discussion 详情页，右上角保留 GitHub 外链。

### Daily brief

日报是按用户时区回顾“昨天”自然日的回顾视图，不是长期归档报告。它把一个本地自然日内的变化重组为两部分：

- 时间窗口：以 `daily_brief_time_zone` 解释本地自然日，窗口固定为「昨日 00:00（本地）→ 今日 00:00（本地）」。
- 自动出报：管理员运行时设置 `daily_brief_schedule_local_time` 决定系统每天几点自动生成日报；首次启动时默认值由 `AI_DAILY_AT_LOCAL` 种子提供，不再由用户单独设置，也不参与内容取数窗口。
- 内容结构固定为：
  - `## 项目更新`：始终存在，按项目组织发布记录与实际变化；同一项目一天多个版本可以合并叙述，并保持变化所属版本清楚。原文不足时应分析可用代码差异；核查后仍无有效变更信息时，保留仓库与版本的最简发布记录，不补正文子要点。处理尚未完成、失败与契约不兼容应单独表达状态，不能写成变更要点；若当天没有 Release，则显示 `- 本时间窗口内没有新的 Release。`
  - `## 获星与关注`：仅当同一自然日内实际存在 `repo_star_received` 或 `follower_received` 动态时出现；只渲染有数据的 `### 获星` / `### 关注` 小节，不再输出空社交占位
- 链接策略：
  - release 主链接：站内链接 `/<owner>/<repo>/releases/tag/<tag>?from=briefs`，点击后在 `日报` 上下文展示详情卡
  - 不另列“相关链接”“来源”“发布原文”或“实现依据”区，也不在每个要点后追加 PR / compare 流水账。现有主入口、原文切换和 GitHub 动作承担上下文核对
  - 安全公告、迁移指南等理解或操作所必需的链接直接可见；确需在正文引用 PR 时，文字明确写为 `PR#编号`
- 正文约束：
  - 卡头负责展示日期、时间窗口与边界信息；正文不再重复输出时间窗口/项目计数等概览元数据
  - 落库前会剥离整篇外层 Markdown code fence，避免整篇日报被当作代码块渲染
  - Release 要点默认按简体中文整理；代码标识符、commit type、包名、API 名、项目名、版本号和原始标题可保留英文
  - 当 AI 不可用或返回不可解析结果时，不把处理提示塞入正文子要点，也不直接把原始 release notes 当作中文要点；已有有效内容与真实处理状态分别保留
- 日报保留 Release 的站内主入口；必要的安全、迁移或操作链接直接出现在变化说明中，不自动追加“相关链接”“来源”或 compare 流水账。
- 用途：让用户快速了解昨天一整天发生了什么，并能一跳查看完整上下文。

上述内容选择是产品合同，不表示全局路径已经完成全部实现；已知内容生成与日报消费偏差见 [Release 阅读内容实现状态](./specs/release-reading-content/IMPLEMENTATION.md)。

## 前台界面结构

### Landing

Landing 负责公开入口和登录承接：

- 解释产品在整理什么信息
- 说明它不是什么
- 提供 GitHub / LinuxDO OAuth 登录入口
- 提供 Passkey 直登，以及“先创建 Passkey、再继续绑定 GitHub”的首登入口

Passkey 只是补充登录方式；正式可用账号仍然要求至少一条 GitHub connection。Landing 不在这里展开复杂配置说明。

### Dashboard

Dashboard 采用主列 + 侧栏结构，核心标签为：

- `全部`（canonical path：`/`）
- `发布`（canonical path：`/releases`）
- `加星`（canonical path：`/stars`）
- `关注`（canonical path：`/followers`）
- `日报`（canonical path：`/briefs`）
- `收件箱`（canonical path：`/inbox`）

桌面端 `全部` 页的右栏保留 Inbox 快捷入口；`/focus/following` 和 `/focus/mine` 的仓库列表沿用相同的视口边界规则。列表短于两张仓库项目卡时，面板填充到固定页脚上方 `16px`；较长列表在面板内滚动。移动端继续使用正文流。

右侧侧栏长期承担 Inbox 快捷入口；在 `日报` 标签下还同时承担日报列表。Release 详情的 canonical deep link 采用 `/<owner>/<repo>/releases/tag/<tag>?from=<tab>`，其中 `from` 只表达返回上下文，默认 `briefs`。登录态 announcement 详情的 canonical deep link 采用 `/<owner>/<repo>/discussions/<number>?from=<tab>`；命中后仍留在 Dashboard 壳层内阅读，不提供独立 public announcement page。

### Focus pages

`/focus/*` 是按仓库、仓库集合、组织、个人仓库或关注仓库收窄的只读信息流。它保留与 Dashboard 一致的自然日分组和原始卡片阅读能力，但不消费全局日报：已有日报、日报覆盖关系、日报/列表切换及日报生成状态都不会进入 focus 页面，也不会隐藏当前 scope 内的原始仓库动态。

### Web Demo

`/demo/` 是公开页面级验收面，不承担真实业务写路径。它复用同一套路由与页面组件，但在 `demo=<scene-id>` 下强制进入 mock-only runtime，并通过 inspector 暴露 persona、network、关键 toggle 与 simulated write 行为。

#### 全部

用统一时间线混排发布更新、获星与关注动态。历史日组会优先折叠成日报卡片；当用户切换到列表视图时，再展开原始活动卡片。

#### 发布

只展示 Release 信息流，并按本地自然日分组。用户在这里主要做“连续阅读”和“切换 lane”。

#### 加星 / 关注

只保留社交动态条目，目标是让用户快速判断“谁在给我反馈”，而不是扩成完整社交 feed。

#### 日报

左侧是日报阅读与手动生成，右侧是日报列表和 Inbox 快捷入口。

#### 收件箱

站内只做通知入口与列表，不接管 GitHub 完整通知工作流。

## Release 阅读模型

发布条目支持 `原文 / 翻译 / 润色` 三种阅读模式：

- 默认优先帮助用户快速扫读
- 保留原文作为最终核对入口
- 在日报中，Release 主入口进入站内详情弹窗，而不是把正文重新塞回主列

详情弹窗保留 Markdown 结构，并提供 GitHub 外链按钮查看原始 Release。

公告条目复用同一套 `原文 / 翻译 / 润色` 阅读模型；feed 中正文可被截断，但进入站内 discussion 详情页后必须始终读取完整正文，并默认显示 `润色` lane。

### Release 内容编辑合同

- **原文**保留发布者提供的内容；**翻译**忠实表达原文；**润色**基于可核实事实组织实际变化、影响、使用条件与必要操作，不能退化为换一种语言完整保留发布模板。
- 标题已说明全部有效信息时，正文可以省略。卡头已明确单一版本时，正文不重复版本号；多产品、组件版本或升级范围所需的版本区别应保留。
- 无阅读价值的贡献归属、PR 流水账与模板废话直接删除，不搬进折叠区，也不增加来源区。生成过程保留核对事实的能力，正文不自动附带取证报告。
- 实际变化、重要限制、兼容性影响与必要操作直接展示。不能因为内容被归为测试、CI 或内部维护，就折叠可读变化。
- 只有有实际核验价值、但通常无需逐字阅读的机器材料可以折叠，例如完整构建指纹与制品清单；日报省略这些材料。没有正文的最简发布记录是紧凑条目，不属于内容折叠。
- Release 原文无实质内容时，生成过程应分析合适范围的代码差异；比较基线必须考虑发布系列、通道与提交关系，不能机械选发布时间相邻的 tag。没有证据时不推断新增能力、性能收益或稳定性提升。
- Feed、详情与日报应共享变更事实与内容结论，排版不决定摘要是否存在。尚未完成、失败、无有效变更信息与契约不兼容不能互相替代。

完整要求与验收场景见 [Release 阅读内容与变更依据](./specs/release-reading-content/SPEC.md)，当前实现缺口见其 [IMPLEMENTATION.md](./specs/release-reading-content/IMPLEMENTATION.md)。

## 翻译策略与需求窗口

AI 翻译不是一次性批处理后静态展示，而是结合同步预热与前端可见窗口触发：

- 同步 release 时，为新增内容补后台翻译任务
- 前端根据真实可见窗口和后续连续卡片，批量请求结果状态
- 已有 ready 译文时，后续 refresh 不会先把界面打回空白“翻译中”
- 自动轮询不会无脑重试 `error`；显式用户动作才触发重试

目标是让用户在真实阅读路径上尽快得到可展示结果，而不是把翻译系统设计成另一个需要单独操作的工作台。

## 日报自然日与时区

- 内容窗口固定为用户本地自然日 `00:00 -> 次日 00:00`
- 自动出报默认时间是 `06:00`，由管理员统一配置；它只影响任务何时触发，不影响内容归属
- 计算使用服务端约定的 IANA 时区，而不是浏览器瞬时时区
- 支持管理员运行时配置统一调整自动出报时刻，用户仅维护日报归属时区

这个约束的意义是保证“昨天更新”在不同设备上仍有稳定口径。

## 权限模型

### GitHub OAuth

OAuth 负责：

- 登录
- 首次账号创建 / GitHub 绑定
- Feed / Notifications / Starred / Releases / Followers / owned repo stargazers 同步

OAuth 默认走最小权限，不为站内 reaction 写操作额外申请权限。

### Passkey

Passkey 是补充登录因子，不是独立账号体系：

- 已绑定账号的返回用户可直接使用 Passkey 登录
- 匿名用户可先创建 Passkey，再继续绑定 GitHub 完成首登
- 设置页支持多设备追加与撤销
- 进入主产品前仍然要求至少一条 GitHub connection

### GitHub PAT

PAT 只用于 Release feedback 写操作，和 OAuth 通道分离：

- 未配置 PAT：reaction 只读
- 已配置且有权限：允许站内点按 reaction

当用户点击 reaction 且未配置 PAT 时，必须通过对话框引导配置，而不是只在卡片底部报错。

## 数据语义

- SQLite 是本地缓存与派生层，不是最终事实源
- Release 以稳定 `release_id` 为共享事实主键
- Star 影响的是“当前用户看哪些列表/日报候选”，不决定 release 详情本身是否仍存在

因此：

- 列表和日报具有个性化可见范围
- 详情读取与详情翻译遵循共享事实语义

## 后台与运维面

管理员任务中心主要处理三类问题：

- 同步与调度是否在正常推进
- 翻译批次、请求与 worker 是否健康
- LLM 调用、并发与输入预算是否符合当前运行配置

这些页面服务于可观测性与运行时控制，不属于普通用户的阅读主路径。

## 非目标

- 不做完整 GitHub 客户端
- 不在站内承接评论、合并、通知已读等完整交互
- 不扩成多语言产品设置页；当前文案口径固定中文
- 不依赖持续后台全量自动同步来塑造主体验，用户仍可主动触发同步
